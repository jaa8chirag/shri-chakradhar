# Decisions Log

Ambiguities resolved without stopping, per the build brief's working-style rule. Real blockers still stop and wait for a "go".

## CP-0 — Data Extraction

- **Package manager / scaffold**: pnpm wasn't installed on this machine; installed via `npm install -g pnpm` (corepack's own pnpm install hit an `EPERM` writing to `Program Files`, so corepack was abandoned in favor of a plain global install).
- **Next.js version**: `create-next-app@latest` installs Next 16 by default. The brief pins Next.js 15 explicitly, so dependencies were pinned back to `next@^15.5.0` / `eslint-config-next@^15.5.0` after scaffolding, keeping React 19.
- **Project folder name**: `create-next-app` refused to scaffold directly into `Shri Chakradhar` (spaces + capitals violate npm package-name rules). Scaffolded into a temp `shrichakradhar-demo/` folder, then moved all files up to the repo root and removed the temp folder. `package.json`'s `name` field stays `shrichakradhar-demo`.
- **robots.txt findings** (see `/data/raw/_robots/*.txt`): all 5 domains allow `/wp-json/` — none disallow the WooCommerce Store API or WP REST API. Only `wp-admin`, feeds, tag archives and cart-tracking query params are blocked. No site required stopping for a CSV/XML export on robots grounds.
- **ignouproject.com has no WooCommerce**: confirmed via `/wp-json` namespace listing — no `wc/*` namespace registered at all. This brand sells a custom project-writing *service*, not a product catalog. Its content (service description, pricing tiers, process) will come from `wp/v2/pages` + homepage HTML instead of `catalog.json`. It still gets a `ProjectJob` flow in the admin (CP-3) rather than storefront products.
- **ignousolvedassignment.com Store API is broken**: `wc/store/v1/products` returns HTTP 500 consistently (categories/tags endpoints on the same namespace return 200 — it's a bug in their product serialization, not a permissions block, and not something to route around covertly). Its `/shop/` and category pages render products client-side via that same broken Store API, so plain HTML fetches of those listing pages come back with empty product grids.
  - Fallback used: `wp/v2/product` (the product custom-post-type is exposed via the standard WP REST API) gives the full lightweight product list (title, slug, full content, category/tag term IDs) cheaply via pagination — this is complete for all ~3,800 products.
  - Real price/SKU/image per product requires fetching each product's own page and reading WooCommerce's standard `data-product_variations` attribute (server-rendered progressive-enhancement data, not scraped from a private API) — at the mandated 1 req/sec that's roughly an hour for this one brand, so it runs as a background extraction pass while the other 4 brands' fast bulk-API extraction runs in parallel.
  - Flagged in `REPORT.md`/`stats.json`: recommend the client's WooCommerce CSV export for this brand as the durable fix instead of relying on the slow per-page fallback long-term. The CSV/XML importer (`import-csv-xml.ts`) is built and wired up regardless, per the brief, so dropping an export into `/data/import/ignousolvedassignment/` works immediately whenever it's available.
- **Sitewide product-tags pagination capped at 10 pages (1,000 tags)**: shrichakradhar.com's `wc/store/v1/products/tags` collection reported 921 total pages (~92,000 tags) — almost certainly SEO-plugin-generated near-duplicate keyword tags, not a meaningful taxonomy. The normalizer never reads this standalone collection anyway (each product's own response already embeds its `tags: [{id,name,slug}]`, which is what dedup/categorization uses), so exhaustively paginating it would have cost ~15 minutes per affected site for zero downstream benefit. Capped via `MAX_TAG_PAGES` in `fetch-wc-store.ts` instead of removing the call outright, so the brief's spec'd endpoint is still hit and a representative sample is cached.
- **Content policy enforcement caught in visual QA**: the first `/design` page screenshot surfaced real "Handwritten Assignment" products in the sample data — a service line the brief explicitly excludes (section 10). Added `lib/content-policy.ts`: `isHandwrittenAssignment()` filters those products out entirely before dedup (102 excluded in this run), and `scrubOverclaims()` removes the specific banned phrasing ("assured N+ marks", "guaranteed acceptance", "A+ guarantee") from descriptions. Deliberately narrow: real product copy mostly uses the word "guarantee" *honestly*, to disclaim outcomes ("No claim is made about the marks...", "not a guarantee") — blanket-stripping the word would have deleted good-faith disclaimers, so only the specific overclaim phrasing is targeted.
- **Playwright added as a dev dependency** (not in the original stack list) to actually screenshot pages during development and catch issues like the one above — a static curl/type-check pass wouldn't have caught the handwritten-assignment content leak. `scripts/screenshot.mjs` is a throwaway verification helper, not a deliverable.
- **Order/project-job persistence uses local JSON files** (`data/runtime/orders.json`, `data/runtime/project-jobs.json`) behind `lib/orders-store.ts`, per the brief's "no database for the demo, but keep the repository interface clean" instruction. This works correctly for local dev and demo walkthroughs. Known gap for CP-6: on Vercel's serverless runtime the filesystem is ephemeral/read-only per invocation, so writes here won't reliably persist across requests once deployed — flagging this now so it lands in the README's "known gaps" section rather than being a surprise at deploy time. Swapping `lib/orders-store.ts`'s internals for a real database later doesn't touch any call site.
- **Brand colors refined from real product art, not just CSS scraping**: automated CSS-variable scraping (`fetch-homepage.ts`) found no usable theme color on most of these sites (no standard variable name — tried Elementor/Astra/Divi/WP-core patterns and `theme-color` meta, still came up empty on 4 of 5). Whole-logo and whole-image "dominant color" via `sharp` also failed — logos and covers are mostly white background, so dominant color was just near-white/near-black noise. What worked: clustering saturated (non-gray) pixels across ~15-40 real downloaded product cover images per brand (`scripts/extract/sample-brand-colors.mjs`, a one-off analysis script, not part of the pipeline) to find the actual recurring accent color. Result: shrichakradhar and ignousolvedassignment are genuinely orange-branded (`#f2820a`, `#f0691e` — confirms what's visible in their real book-cover template); ignoustudymaterial's real covers turned out to be a dark navy/monochrome design, not the bright orange originally guessed, so its fallback was corrected to `#1e293b`. ignouquestionpaper didn't have enough downloaded images yet to sample confidently, so it keeps a reasoned manual guess (`#b91c1c`, red — common for "exam paper" branding) pending a re-sample once more of its product images finish downloading.
- **Fixed a lazy-load logo bug**: the homepage scraper's logo selector was grabbing `src` directly, which on lazy-load-plugin sites is a blank placeholder (`data:image/svg+xml,...`) — the real logo lives in `data-src`/`data-lazy-src` until JS swaps it in. `fetch-homepage.ts` now checks those attributes first and rejects `data:` URIs.
- **Split rarely-read fields out of catalog.json for performance**: at ~17k merged products, `catalog.json` hit 99MB — half of it `description` HTML that only the single product-detail page ever renders, plus unused-at-runtime `categories`/`tags` arrays (grep confirmed nothing in `app/`/`components/` reads `product.categories` or `product.tags`; `categories.json`, the separate Level→Programme→Course tree, is what the UI actually uses). Moved `description`/`shortDescription`/`categories`/`tags` into `data/clean/product-details.json`, hydrated only by `getProductBySlug` (`lib/data.ts`) — browse/search/home now load an 18MB catalog instead of 99MB. Also capped `images` at 5 per product (one outlier had 30, inflating the merge).
- **Unified single-store redesign (client-requested revision)**: replaced the original "5 brand storefronts + landing page picker" architecture with one unified store where Shri Chakradhar Publication is the master brand and the other 4 sites become sections (Study Material, Solved Assignments, Question Papers, Guess Papers, Projects & Synopsis), each keeping its own logo as a sub-brand badge in that section's mega-menu/hero. A product's section membership is derived purely from its `type` field (`lib/sections.ts`) rather than a brand-union list — since the master brand's own catalog already spans every type, filtering by type alone naturally pools shrichakradhar's matching products into each section alongside the specialist brand's. Routes moved from brand-scoped (`/s/[brand]/browse`, `/s/[brand]/p/[slug]`, `/s/[brand]/cart`, ...) to global (`/study-material`, `/product/[slug]`, `/cart`, ...); old `/s/[brand]/*` URLs now redirect to the matching section so old links/bookmarks still resolve. `FilterPanel`/`SortSelect` were generalized from a `brandId` prop to a plain `basePath` string so they work against any route, not just brand-scoped ones.
- **Logo extraction fixed with a 4th fallback source**: `og:image` and header `<img class="logo">` selectors found nothing for 2 of the 5 sites (Woodmart-themed stores with no recognizable logo markup). Added JSON-LD `Organization.logo` parsing (populated by Rank Math/Yoast regardless of theme) as a new source, checked before falling back to the WP REST API's `site_icon_url` — between the two, all 5 brands now resolve to their real, correctly-sized wordmark logo instead of a broken image or a 16px favicon stretched to header size. Also added a `minWidth` rejection (raster logos under 120px wide are treated as unusable, falling through to `BrandLogo`'s colored-initials wordmark) per the client's explicit ask — SVGs are exempt since they're resolution-independent.
- **Fixed a real slug bug affecting ~5% of the catalog**: WordPress stores some Hindi-titled products' slugs as literal percent-encoded ASCII text (e.g. `...%e0%a4%b8%e0%a4%ae...`) instead of decoded Unicode. Next.js's dynamic route matching doesn't reliably resolve a param containing raw `%XX` sequences that aren't meant as encoding, so these product pages 404'd. `normalizeSlug()` in `normalize-catalog.ts` decodes any slug containing `%` once at build time, giving a normal Devanagari slug that routes like any other UTF-8 URL segment.
- **Course-code parsing**: normalized to `LETTERS-DIGITS` (e.g. `MMPC-001`, `BEGC-134`). Padding is preserved exactly as found in the source text rather than invented, since IGNOU itself is inconsistent (e.g. "MEG 1" and "MMPC 001" are both real, distinct codes) — inventing padding would silently merge or split real codes.
